# 思考题

来源：[第 1 章 · Agent 基础知识](https://bojieli.github.io/ai-agent-book/book/chapter1/)

1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

答：我会选择更丰富的上下文。Agent系统=模型+上下文+工具。假如一个人现在的任务是补全哈利波特的最后一段。我们考虑他可能看到不同范围的哈利波特，他的智力水平也可能处在不同范围，以及完成任务需要必要的工具，例如纸、笔。假如他智力正常，并且也有纸和笔了，但是只能看到前6本，最好是直接给他最后一本。如果他已经能看到所有的哈利波特（除了最后一段），并且也有纸笔，但是他太弱智了连字都不会写，那么就换一个人来写。假如他智力正常，也能看到足够多的哈利波特，但是没有纸笔，就给他纸笔。有时候他可能需要一些工具来看完所有的哈利波特，例如一部份文本是在网上的，那么就给他电脑和网络。

预测损失的分解：条件熵 + 模型误差。设上下文与目标答案服从真实联合分布 $(C,Y)\sim p^*$，模型的预测分布为 $p_\theta(Y\mid C)$。固定上下文的构建方式，定义平均负对数损失：

$$
\mathcal L(\theta)
=
\mathbb E_{(C,Y)\sim p^*}
[-\log p_\theta(Y\mid C)].
$$

在对数中引入真实条件分布 $p^*(Y\mid C)$：

$$
-\log p_\theta(Y\mid C)
=
-\log p^*(Y\mid C)
+
\log\frac{p^*(Y\mid C)}{p_\theta(Y\mid C)}.
$$

两边对真实分布取期望，得到：

$$
\begin{aligned}
\mathcal L(\theta)
&=
\mathbb E_{p^*}[-\log p^*(Y\mid C)]
+
\mathbb E_{p^*}
\left[\log\frac{p^*(Y\mid C)}{p_\theta(Y\mid C)}\right]\\
&=
\boxed{
H_{p^*}(Y\mid C)
+
\mathbb E_{C\sim p^*}
D_{\mathrm{KL}}
\left(p^*(Y\mid C)\,\|\,p_\theta(Y\mid C)\right)
}.
\end{aligned}
$$

- **条件熵 $H_{p^*}(Y\mid C)$ **：给定现有上下文，答案仍有多少不确定性；它是该信息条件下的最低平均对数损失。
- **平均 KL 散度**：模型预测偏离真实条件分布带来的额外损失；非负，分布一致时为零。

因此：

$$
\boxed{
\text{平均预测损失}
=
\text{现有信息下的不确定性}
+
\text{模型预测的额外误差}
}
$$

**对 Agent 的启示**：前项大，优先检查能否补充有效信息；后项大，优先检查如何改善信息利用，例如换模型、重组上下文或使用计算工具。最终选择取决于可实现的损失下降，而非哪一项当前更大。

> 适用范围：使用对数损失的预测任务；不能直接替代一般 Agent 的任务成功率、执行成本等评价。推导假设相关概率与期望定义良好，且模型在真实分布的支持集上赋予正概率。

1. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

答：【为什么累计缓存读取量随轮数近似二次方增长？】

一个ReAct循环中，模型的上下文=静态前缀 S + 动态轨迹。假如每一轮新增长的轨迹长度为 L，那么第 i 轮的模型的上下文长度为：S+(i-1)L。生成第 i 轮的token时，读取的缓存长度为 S+(i-1)L，即已经缓存的前缀的K、V，长度约等于当时的上下文。那么 n 轮累计缓存读取量为 $\sum_{i=1}^n S+(i-1)L=nS+Ln(n-1)/2=O(n^2)$。

【如何降低这种增长？】

上下文长度达到某种阈值时，压缩已有的上下文，例如做摘要，以及存到外部存储中让模型按需读取。这样可以减少 Ln(n-1)/2 这一项。

用子Agent隔离。相当于把中间多轮的上下文由子Agent承担。减少了n这一项。

不能每轮压缩：会伤性能，还多一次压缩调用，并且改前缀会逼缓存重建。

1. ★★ “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

harness为模型提供更多的工具，优化模型的上下文，以及提供权限管理等安全护栏。首先是让越来越自主的模型的行为在人类允许的约束内，禁止做出不安全行为。其次给模型提供一个思维的约束，按照更高效的方式思考（例如gpt 5.6不要想哥布林）。为模型进行轨迹记录，以便后续的测评、重放等。这一点也有助于收集真实生产环境里的agent轨迹，为后训练提供数据。

标答：模型越强、自主空间越大，出错影响面越大，越需要约束、验证、纠正；框架价值从「编排 LLM 调用」转到保障层——权限分类、熔断器、错误恢复、上下文压缩、工具生态。

1. ★★ 消融实验中 “工具结果反馈” 的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？

答：还可能是agent无法看到推理内容和过去的轨迹。检测模型每次输出和上一次的相似性。如果相似超过一个阈值则种植。或者检测轮数超过最大阈值则终止。

【标答】：从Agent=模型+上下文+工具的角度思考，陷入循环还包括：1）工具调用持续出错，2）模型出现幻觉调用不存在的工具，3）上下文中的关键状态、关键决策被压缩丢失，4）模型无法看见自身的推理轨迹，5）任务无解。

检测和终止：1）设置硬上限，如最大轮数、最大工具次数、最大墙钟时间；2）重复指纹， 对 `(工具名, 规范化参数)` 做哈希。同一指纹连续出现 k 次（或短窗口里占比过高），就判定循环。空结果、同一错误、幻觉工具，都会打在同一个指纹上；3）失败升级。 同一工具失败 n 次，或已判定循环：停下来，交给人。

1. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？
答：工作流模式：查询航班信息-检查顾客信息-提交支付-返回结果。可能，例如在查询航班信息时自主理解顾客意图，为顾客推荐符合要求的多个航班。但是后续的步骤涉及信息合规、订单、支付等有严格安全要求的动作，故还是用工作流模式。

【标答】身份核实 → 搜索 → 付款 → 预订。禁止跳步。理解需求、多航班推荐、改签和取消后的方案用自主 Agent，搜完再交回工作流。大额支付和退款必须人确认。这样既保留开放理解，又把合规和不变量放在图上，而不是放在模型自觉里。

2. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
答：评级对象从“工具”细化到“工具+参数”：调用时根据可逆性、权限和影响面计算风险。采用基于规则的确定性检查（路径黑白名单、正则），而非模型判断。验证时应只检查结构化数据，防止提示注入操纵判断结果。

3. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是 “开放式” 的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？
答：高合规、高风险、不可逆的场景下。
4. ★★ 人工干预机制要求 Agent 能 “优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？
Fail-safe：高风险操作在未获确认时暂停，而非默认执行；先完成可逆的低风险部分，将高风险部分记录在文档中，便于人类决策和 Agent 恢复；使用异步沟通工具（消息、邮件）通知用户并设置超时策略；指令模糊时先澄清意图。【我们希望agent有清晰的目标，规避高风险，并且受人类监管确认】
5. ★★★ 引言指出 “好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。
【标答】：示例一：通过约束采样强制工具调用符合严格格式。这是在模型容易输出非法 JSON、遗漏参数时采用的可靠性补丁；随着模型的格式遵循能力提高，其收益可能逐渐降低，但高风险场景仍应保留确定性的格式校验。

示例二：为弥补模型无法持续吸收新知识而引入外部知识库。如果模型未来具备可靠的持续学习能力，一部分知识维护可能从模型外部迁移到参数中。不过，外部知识库在实时更新、精确检索、权限控制和来源追溯方面仍有独立价值，因此更可能缩小适用范围，而非完全消失。

示例三：要求所有能力都必须通过模型 API 的标准工具调用接口暴露，禁止自定义调用形式。Skills 已经展示了另一条路径：用文本描述能力及操作方法，再让模型通过通用命令行工具执行；从模型视角看，这相当于在通用执行器之上理解并遵循一种自定义的文本调用协议。随着模型理解任意接口的能力增强，“必须使用标准工具调用格式”不再适合作为普遍原则。标准格式对于互操作、结构化校验以及能力较弱的模型仍然有用，但它应是基于场景的工程选择。

示例四：要求提示词与全部工具定义必须预先放在上下文开头。这种做法源于早期模型的指令遵循能力有限，提示或工具定义离开熟悉的固定位置后，模型往往难以正确识别和执行。Skills 会在运行过程中按需把提示词加载到上下文中间；动态工具发现也会在找到新工具后，把工具定义追加到已有轨迹之后。随着模型的指令遵循能力增强，以及针对这类动态加载方式进行专门的后训练，提示词和工具定义不再必须固定在上下文开头。
