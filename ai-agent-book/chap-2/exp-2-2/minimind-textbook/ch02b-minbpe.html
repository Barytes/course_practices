第 2.5 章 · 亲手写 BPE：minbpe

第 2 章把分词器当成黑盒来用。这一章把它拆开：从 UTF-8 字节出发，反复合并最常见的相邻对，直到词表够用。算法来自 Andrej Karpathy 的 minbpe。章末是 Let’s build the GPT Tokenizer 的完整中文文字稿。

没有它，第 2 章只剩口号

第 2 章说：BPE 从字节出发，把高频片段焊成新词元。这句话如果不能用手算、不能用代码复现，就还是口号。Karpathy 写 minbpe 的动机正是这个：tiktoken 很快，但看不清；把训练、编码、解码写成能读完的 Python，词表是怎么长出来的才会变成肌肉记忆。

这一章不替代 MiniMind 官方的 tokenizer.json。作业模型仍然加载那份 6400 词表。你在这里练的是同一类算法的显微镜版：打开 exp-2-2/bpe/，搜 # >>> 填空，把 minbpe 的核心循环自己写完。进度见同目录的 exercise.md。

和官方仓库怎么对应

BasicTokenizer 在 minbpe/basic.py，两个工具函数在 minbpe/base.py。下面的代码按它的语义重写，变量名故意写得更直白。原仓库还有 RegexTokenizer（GPT-2/4 那种按类别先切开再合并）和 GPT4Tokenizer（对齐 tiktoken 的 cl100k_base）。先把 Basic 写对，再谈那两层皮。

为什么从字节开始，而不是从汉字开始

第 2 章的字符级草稿按 Unicode 码点切：「天」永远是一个编号。BPE 先把字符串编成 UTF-8 字节，每个字节是 0–255 的整数。英文 A 是一个字节 65；汉字「天」是三个字节 e5 a4 a9。词表的前 256 项永远预留给这 256 个字节，后面的编号才是合并出来的。

词表大小 = 256 + 合并次数（特殊标记再接到后面）
minbpe 的 train(text, vocab_size) 里，合并次数就是 vocab_size − 256。MiniMind 的 6400 还要再扣掉一批特殊标记，数量级仍是「几百字节 + 几千次合并」。

这件事有一个立刻能感到的好处：不会出现「这个字不在词表里」。再罕见的符号也能退回成字节。代价是：训练刚开始时，一个汉字往往占 3 个词元；合并足够多次之后，「天」「天空」才可能各自变成一个编号。这就是第 2 章说的压缩率从哪来。

两个会反复用的函数

整套算法只靠两块积木。第一块统计「相邻两个编号」出现了几次；第二块按从左到右、互不重叠的方式，把某一对换成新编号。

现在动手 · 写到哪里

文件exp-2-2/bpe/minbpe/base.py（搜 # >>> 填空）
符号函数 get_stats、merge
怎么跑先在本页上方的小实验点「合并一步」建立直觉，再去填空。跑 pytest -v tests/test_tokenizer.py::test_wikipedia_example
对应原理「数相邻对出现几次」+「从左到右、互不重叠地焊成新编号」。

重叠要小心：aaa 里有两处 aa，但一次扫描只能焊左边那对，得到 [aa] a，不是 a [aa]。BPE 的约定就是从左到右、互不重叠。不要写成「全局字符串 replace」，那会和编号列表的语义拧在一起。

代码怎么对上原理

  • zip(ids, ids[1:]) → 把序列看成前后错开的两列，每一对相邻编号数一次。
  • i += 2 当焊中时 → 互不重叠。焊了左边的 aa，右边那个 a 留给下一轮。
  • 新编号 idx 从 256 起发 → 0–255 永远留给字节，合并出来的词元不会把字节表挤掉。

Wikipedia 那道必算的例题

BPE 词条用字符串 aaabdaaabac 做演示。minbpe 的 README 也从这里开始。先把字母换成 ASCII：a=97, b=98, c=99, d=100，然后做 3 次合并。请你先手算，再和下面的表对答案。

步当前序列最常见对新编号新词元
0a a a b d a a a b a c(a, a) 出现 4 次256aa
1[aa] a b d [aa] a b a c([aa], a) 与 (a, b) 都是 2 次257aaa
2[aaa] b d [aaa] b a c([aaa], b) 出现 2 次258aaab
3[aaab] d [aaab] a c——编码结果 [258, 100, 258, 97, 99]

三次合并之后，11 个字节变成 5 个词元。258 覆盖的是整段 aaab，不是单个字母。

平票时，代码说了算

百科叙述常把三次合并讲成 aa → Z，ab → Y，ZY → X。minbpe 在第 2 步遇到平票：(256, 97) 和 (97, 98) 都出现 2 次。Python 的 max(stats, key=stats.get) 取先写进字典的那一对，于是焊的是 aa+a → aaa，而不是 ab。最终编码仍是 [258, 100, 258, 97, 99]，因为 258 照样盖住了 aaab。读 README 时对一下源码：叙事可以换一种树，编号列表碰巧长得一样。

自己点一步，看合并怎么发生

下面这个小实验跑的就是上面两个函数。默认语料是那道例题。改成中文再训几次，你会看见一个汉字先占 3 个字节，随后才被焊起来。

相邻对次数若合并得到

    「合并一步」每次只焊当前次数最高的一对。编码规则还没上场——那是下一节。

    训练：反复焊最常见的一对

    train 就是一个 for 循环。每一轮：统计、取最大、发一个新编号、全表替换、记下「哪一对变成了几」。循环结束时，你得到两张表：

    • merges：(id_a, id_b) → 新 id，编码时用。
    • vocab：id → bytes，解码时用。新词元的字节等于两个孩子的字节直接拼接。

    现在动手 · 写到哪里

    文件exp-2-2/bpe/minbpe/basic.py 的 BasicTokenizer.train
    下面这段是语义对照，变量名更直白。真正交作业请填 basic.py 里的空，不要另建一套类。

    注意 train 结束时的 ids 只是这份训练语料被压短之后的样子，不要拿它当编码器。编码器必须能处理训练时没见过的字符串，规则在 merges 里。

    train 怎么对上原理

    • list(text.encode("utf-8")) → 从字节开始，不是从汉字开始。
    • max(stats, key=stats.get) → 「焊当前最常见的一对」。平票时 Python 取先写进字典的那一对。
    • self.merges[pair] = idx → 菜谱。编码时按这份菜谱走，不再数频率。
    • self.vocab[idx] = vocab[a] + vocab[b] → 新词元的字节 = 两个孩子直接拼接，解码才变回字符串。

    编码：按合并出生顺序，不是按当前频率

    这是整章最容易写错的一行。编码时如果再「焊当前最常见的一对」，同一套 merges 在不同句子上会走出不同的树，模型看见的编号就不稳定。正确规则是：

    在当前序列里，选 merges 中编号最小的那一对来焊；一对都焊不了就停
    编号小 = 训练时更早出现。后出生的词元是由先出生的词元拼出来的，必须先还原祖先，再还原后代。

    min(..., key=merges.get 缺省为 inf) 的意思是：不在 merges 里的对，优先级是无穷大，永远不会赢。若所有对都是无穷大，min 会随便返回字典里的第一对——所以必须再写 if pair not in self.merges: break。这不是雕虫，是 Karpathy 在源码注释里专门标出的终止条件。

    解码反而简单：每个编号查成字节，拼起来，按 UTF-8 解。某个词元可能只是半个汉字（三个字节里的前两个），所以 errors="replace"：单独解码会看到 �，但相邻词元拼回去就合法了。这不是 bug。

    encode 怎么对上原理

    • min(..., key=merges.get 缺省 inf) → 「按合并出生顺序焊」，不是按当前这句话里哪一对最多。
    • if pair not in self.merges: break → 焊不动就停。没有这一行，min 会在全是 inf 时随便返回一对，死循环或焊错。
    • errors="replace" → 半个汉字单独解码会看到 �，拼回去就合法。这不是 bug。

    跑通那道例题

    把 get_stats / merge / BasicTokenizer 填完之后，在 exp-2-2/bpe/ 里跑维基那道例题，检查编号是不是 258 / 100 / 258 / 97 / 99：

    再试一句训练时没见过的：encode("aaab") 应当得到 [258]，因为三次合并的树恰好能覆盖它；encode("cab") 则应退回三个字节编号。编码器没有「未知词」分支，只有「还能不能按菜谱继续焊」。

    RegexTokenizer：先按类别切开，再在块内合并

    Basic 版会把 dog. 焊成一个词元，也会把数字和字母焊在一起。GPT-2 起加了一道预分词：用正则把文本切成「字母块 / 数字块 / 标点块 / 空白块」，合并绝不跨越块边界。minbpe 的 RegexTokenizer 默认用 GPT-4 那条模式；统计次数时把所有块的 get_stats 加总，真正 merge 时却只在各自的块里替换。

    块的种类（直觉）它在防止什么
    字母词，可带前置空格空格常常焊进单词，变成 " dog" 这样一个词元。
    数字每次最多 3 位这是 GPT-4 词表算术别扭的根源之一：677 不一定是一个词元。
    标点、换行句号不会和单词焊死，代码缩进也更稳定。

    Python 标准库 re 不够用，源码依赖 regex 包，因为模式里有 \p{L} 这种 Unicode 属性。作业不要求你复现 GPT-4 词表；知道「MiniMind 用的 Hugging Face tokenizers 也是 ByteLevel + BPE，同样不会跨类别乱焊」就够了。

    特殊标记是另一路编号，不是焊出来的

    合并用完 0 … vocab_size−1 之后，才能登记 <|endoftext|> 这类标记。minbpe 的接口是 register_special_tokens({"<|endoftext|>": 32768})。编码时必须显式允许它们，否则用户输入里一旦出现这段字符串，就会被当成普通文本切开——或者像 tiktoken 默认那样直接报错。这是安全问题，不是风格问题：提示词里不该能偷偷注入「对话结束」。

    MiniMind-3 的 <|im_start|> / <|im_end|> / <think> 走的是同一逻辑，只是登记在官方 tokenizer.json 里。第 15 章会真正用到它们。

    附录 · Let’s build the GPT Tokenizer 文字稿

    整理自 Andrej Karpathy 的讲座 Let’s build the GPT Tokenizer（2024 年 2 月）。配套代码在 karpathy/minbpe。按讲座顺序写成中文，口误、重复和现场跑代码的碎念已理顺，论点按原讲写全。

    开场：分词是最不讨喜、又躲不开的一层

    大家好。这一讲要谈大语言模型里的分词。你看我一脸苦相，因为这是我做大模型时最不喜欢的部分。它又脏又绕，脚下全是暗坑。你在模型上看到的许多古怪现象，追到根上往往不是网络结构的问题，而是分词。

    上一讲 Let’s build GPT from scratch 其实已经做过分词，只是最天真的那种：字符级。Colab 里训练数据是莎士比亚，一开始它只是 Python 里的一长串字符串。怎么把字符串塞进语言模型？我们先扫一遍训练集，把出现过的字符收成词表，一共 65 个：空格、标点、数字、大小写字母。然后做两张查找表，字符换整数、整数换回字符。encode("hii there") 得到一串编号；取前 1000 个字符编码，就得到 1000 个词元，因为一个字符就是一个词元。

    这些整数怎么进模型？靠嵌入表。词表 65，嵌入表就 65 行。每个词元的整数当作行号，抽出那一行可训练向量，再送进 Transformer。Transformer 看见的从来不是字母，是这些向量。

    字符级在玩具设定里够用。真正的前沿模型不在字符上切，而在「字符块」上切。构造这些块的算法，就是字节对编码，也就是 BPE。我们这一讲会把它从头写出来。

    把字节级 BPE 带进大模型分词的，大概是 2019 年 OpenAI 的 GPT-2 论文 Language Models are Unsupervised Multitask Learners。翻到第 2.2 节 Input Representation，他们讨论分词该有哪些性质，最后给出词表 50257、上下文 1024。注意力里每个词元最多看前面 1024 个词元。词元是大模型的原子：训练、推理、计费，全按词元算。分词就是在原始字符串和词元序列之间做翻译。Llama 2 论文里搜 token，能命中六十多次，他们写自己训了两万亿词元——可见这个抽象有多无处不在。

    好消息是 BPE 本身并不玄。我们可以从零写。进代码之前，先尝一口它有多「脏」，免得你觉得这层可以敷衍过去。

    语言模型的许多怪癖，看起来像模型不行，其实是分词：

    • 为什么不会拼写？分词。
    • 为什么连反转字符串这种小事都做不好？分词。
    • 为什么非英语（比如日语、韩语）明显更差？分词。
    • 为什么简单算术也别扭？分词。
    • 为什么 GPT-2 写 Python 特别费劲？分词。
    • 为什么看见字符串 <|endoftext|> 会突然停？分词。
    • 那个 trailing whitespace 警告是什么？分词。
    • 问它 SolidGoldMagikarp 为什么会发疯？分词。
    • 为什么有人劝你用 YAML 而不是 JSON？分词。
    • 为什么语言模型其实不是端到端的语言建模？分词。
    • 痛苦的真正根源是什么？分词。

    这些条目我们讲到最后会一条一条拆开。现在先换个能看得见的界面。

    在浏览器里看分词：tiktokenizer

    打开 tiktokenizer。分词在浏览器里实时跑，左边贴字符串，右边立刻着色。当前用的是 gpt2 词表。我贴进去的那段示例大约 300 个词元。

    单词 Tokenization 被切成两个词元，编号大约是 30642 和 1634。带前置空格的 is 是 318。 at 是 379， the 是 262。底部可以开关空白显示。空格和换行都在字符串里，必须被编码；可视化常常把它们藏起来，容易让人忘了「空格也是词元的一部分」。

    算术更刺眼。127 可能是一个三字符词元；677 却是 6 加 77 两个词元。模型必须在参数里自学：这两个编号拼起来才是六百七十七。若答案是 804，它还可能要分两步吐出：先 8，再 04。四位数同样任意：1275 也许是 12+75，6773 也许是 6+773，8041 也许是 8+041。切法完全由合并历史决定，看起来毫无道理。

    再看 egg。句首的 Egg 是两个词元；I have an egg 里带空格的 egg 变成一个词元。全小写 egg 又是另一个编号，颜色都不同。全大写再换一套。同一概念，句首句中、大小写一变，编号全变。模型只能从海量文本里自己聚类：它们差不多是一回事，但并不完全一样。

    韩语也贴一段 ChatGPT 的自我介绍。非英语差，不全是因为模型训练数据偏英语——分词器的训练数据同样偏英语。英语常见片段会被焊成又长又密的词元；译成韩语、日语，同样一句话往往碎成更多词元。序列被拉长，注意力的有限窗口更快用完。从 Transformer 的视角看，非英语文本是被「拉稀」过的。

    最后是一段 FizzBuzz 风格的 Python。GPT-2 里每一级缩进空格常常是单独的词元 220：220、220、220、220，然后才是 if。模型生成这段代码时，要把这些空格一个一个过完整套注意力。这极度浪费上下文。GPT-2 写 Python 差，不全是「它不会编程」，很大一块是缩进把序列撑爆了。

    同一段字符串，把词表换成 GPT-4 的 cl100k_base，词元数从大约 300 掉到大约 185，几乎腰斩。GPT-4 词表大约十万，GPT-2 大约五万，所以同样文本更密，注意力窗口里能装进大约两倍的原文。词表也不能无限加：嵌入表变大，最后一层 Softmax 也变大。中间有一个「够密又不太贵」的甜点区，后面再谈。

    GPT-4 对 Python 空白的处理明显好了：四个空格、三个空格、七个空格，常常被收成一个词元。这是设计时故意的。从 GPT-2 到 GPT-4 的代码能力提升，不全是架构和优化，分词器怎么把空格焊起来也占了一大截。

    字符串在 Python 里是什么：Unicode 码点

    我们要做的事很朴素：把字符串变成某个固定词表上的整数，再用整数去查向量，送进 Transformer。麻烦在于：不能只支持英文字母，还要韩语「안녕」、emoji、互联网上随便什么符号。

    Python 文档写得很清楚：字符串是 Unicode 码点的不可变序列。码点由 Unicode 联盟定义，当时大约十五万个字符、一百六十一种文字。标准还在长，讲座时最新是 15.1（2023 年 9 月）。

    ord("h") 是 104。那个 emoji 的码点大约在 128000 附近。韩语某字大约五万。ord 一次只吃一个字符，不能丢整串进去。对整句做 [ord(x) for x in s]，已经得到一串整数了。为什么不直接拿码点当词元？

    两个理由。词表会变成十五万这么长；更麻烦的是 Unicode 还在变，不是稳定表示。我们需要更好的一层。

    UTF-8、UTF-16、UTF-32

    Unicode 定义了三种常见编码：UTF-8、UTF-16、UTF-32，把码点变成字节流。UTF-8 最普遍：每个码点变成 1 到 4 个字节，变长。UTF-32 定长，但浪费。三种编码的完整利弊超出这一讲，有一篇我很喜欢的博文，文末还指向 UTF-8 Everywhere 宣言。UTF-8 一个关键优点是向后兼容 ASCII。

    对同一字符串调用 .encode("utf-8") 得到 bytes 对象。UTF-16、UTF-32 对简单英文字母会插进大量零，看起来就很浪费。所以我们钉死 UTF-8。

    可如果直接拿 UTF-8 字节当词元，词表只有 256。嵌入表和最后一层会极小，序列却极长。注意力窗口按词元算，窗口装不下足够原文，下一词预测就近视。我们既想留在 UTF-8 上，又想把词表做成可调的超参数。答案就是 BPE：按可变程度压缩字节序列。

    能不能取消分词？

    我最想做的，其实是把原始字节流直接喂给语言模型。前一年夏天有一篇论文讨论这件事（MEGABYTE 那一类工作）：序列太长，注意力会贵到炸，所以他们给 Transformer 做了层次结构。论文结尾说，这些结果说明「无分词的自回归序列建模在规模上是可行的」。若真能取消分词，会非常美好。但当时还没有足够多的团队在足够规模上把它坐实。眼前我们还是得用 BPE 先压一遍。

    BPE：维基百科那道例题

    BPE 并不复杂，维基百科写得很清楚。假设词表只有 a、b、c、d 四个符号，序列是 aaabdaaabac，一共 11 个位置，太长，要压缩。

    反复做同一件事：找出现次数最多的相邻对，铸造一个新词元，整表替换。最常见的是 aa，铸 Z 替换，11 个位置变成 9 个，词表变成 5。再找，这次是 ab，铸 Y，序列变成 7，词表变成 6。再找，ZY 最常见，铸 X，最后剩下 5 个词元，词表变成 7。

    字节上完全一样：从 256 个字节出发，反复铸造新编号、替换、记进词表。压缩程度由你决定做几次合并。维基那套叙事把树讲成 aa→Z、ab→Y、ZY→X；你自己写代码时平票怎么破，以 max(stats, key=stats.get) 为准。

    开始实现：字节、数对、合并

    先拿一段短文本，text.encode("utf-8") 得到 bytes，再 list(...) 变成 0–255 的整数列表，比直接操作 bytes 对象顺手。

    第一个函数：统计相邻对。zip(ids, ids[1:]) 扫一遍，字典里累加次数。按次数排序，讲座示例里最常见的一对是 (101, 32)，也就是字母 e 和空格，出现 20 次——很多英文词以 e 结尾。

    取最大键：max(stats, key=stats.get)。然后铸造新编号 256（0–255 已被字节占住），从左到右、互不重叠，把每一处 101,32 换成 256。这就是 merge。重叠要小心：aaa 里有两处 aa，一次扫描只能焊左边，得到 [aa] a。

    建议你先自己写这两个函数，再往下看。整套算法之后都在它们上面打转。

    训练：while 换成 for，看压缩率

    短段落统计不稳定。讲座里换成整篇博文拉成一行，字节更长，对的频率才有代表性。编码成 UTF-8，再变成整数列表。

    词表大小是超参数。若已有 256 个字节、想做恰好 20 次合并，就设 vocab_size = 276。复制一份 ids，免得改坏原文。再准备 merges：(子, 子) → 新编号。这不是单根树，而是从 256 片叶子往上焊的森林。

    循环二十次：找最常见对，发新编号（从 256 起），整表替换，记进 merges。第一次仍是 101,32 → 256。101 和 32 单独出现时还在，只有相邻才被焊。新铸的 256 下一轮也可以再被焊：第 20 次合并可能是 256 和 259 变成 275。所以这是森林，不是一棵树。

    压缩率：讲座示例从大约 24000 字节压到大约 19000 词元，约 1.27 倍。合并越多，通常压得越狠。这些 merges 就是分词器的「参数」。

    分词器跟语言模型是两个阶段

    请记住一张图：分词器是完全独立的对象。这一讲几乎不碰 LLM 本身。它有自己的训练集，和语言模型的训练集可以不同；用 BPE 训一次，得到词表和 merges。之后它是翻译层：Unicode 字符串 ⇄ 词元序列，编码、解码两支箭头。

    典型流程是：把语言模型的全部训练数据先过一遍分词器，变成海量词元存盘，原文可以扔掉。模型训练时读的是词元文件。

    两套语料为什么要分开调？因为分词训练集里某种语言、某种代码占多少，会决定那种数据焊出多少词元，从而决定它在词元空间里有多密。日语加得多，日语序列就短，有限上下文里能装更多日语。这是密度分配，不是小事。

    解码：编号变回字符串

    给定整数列表，返回 Python 字符串。先造 vocab：0–255 映射到单字节；再按 merges 的插入顺序，新词元的字节等于两个孩子的字节拼接。从 Python 3.7 起字典保序，才能按插入顺序重建。

    对每个 id 查字节，拼成一大块 bytes，再 decode("utf-8")。默认 errors="strict" 会炸。解码 97 得到 a 没问题；单独解码 128 会报 invalid start byte。UTF-8 对多字节有固定包络，128 的二进制是 1 后面全 0，对不上任何合法开头。

    不是任意字节序列都是合法 UTF-8。模型若吐出一串倒霉编号，就解不回来。标准做法是 errors="replace"，非法处换成 �。OpenAI 发布的代码也这么干。看见 �，说明输出不是合法 UTF-8 词元序列。编码再解码通常是恒等；解码再编码不是，因为有些编号序列根本解不成合法文本。

    空串或单字节没有能焊的对，编码时要先判断 len(ids) < 2，否则 min 会在空统计上翻车。解码函数本身不走合并，只查表、拼接、按 UTF-8 解开。

    编码：按合并出生顺序焊，不是按当前频率

    给定字符串，返回整数列表。先 UTF-8 成字节列表。训练时 merges 从上到下插入：后面的合并依赖前面铸出的编号，所以编码必须先做早出生的合并，再做晚出生的。

    循环里仍用 get_stats，但次数已经不重要，只要当前序列里出现过哪些对。在这些对里，选 merges 中编号最小的那一对。min(stats, key=lambda p: merges.get(p, float("inf")))：不在 merges 里的对优先级是无穷大，赢不了。若所有对都是无穷大，min 会随便返回字典第一对——所以必须再写 if pair not in merges: break。这是终止条件，不是雕虫。

    找到就 merge，直到焊不动。再强调一次：编码时如果再「焊当前最常见的一对」，同一套 merges 在不同句子上会走出不同的树，模型看见的编号就不稳定。

    训练语料 encode 再 decode 应还原；再从网上另抓一段没见过的验证文本，也应还原。注意恒等只保证这一方向：不是所有编号序列都能解成合法 UTF-8，所以 decode 再 encode 不必是恒等。这就是最简 BPE。接下来，前沿模型会把这张图迅速复杂化。

    正则预切分：不许跨类别乱焊

    GPT-2 论文 Input Representation 前面都和我们做的一样，从某一段开始分道。他们举 dog 为例：dog 经常跟句号、感叹号、问号挨着。朴素 BPE 可能把 dog.、dog! 各焊成一个词元，标点和词缠死，实验上也不好。所以他们用正则，自上而下强制：某些类别之间永远不许合并。

    OpenAI 仓库 src/encoder.py 这个名字不好——分词器既能编码也能解码，叫 encoder 很别扭。真正起强制作用的是那条很长的正则。注意他们 import regex as re，不是标准库 re，因为要 \p{L} 这种 Unicode 属性。

    re.findall(pattern, text) 从左到右切出一块块。每一块独立做 BPE，结果再拼接。于是 e 和后面的空格若被切进不同块，就永远不会焊成「e+空格」。

    模式是一串或。直觉上：

    • 常见英文缩写 's 've 're 等，单独切出来。
    • 可选空格加上一串字母 \p{L}+：hello 一块， world 一块。
    • 可选空格加上数字 \p{N}：字母和数字分开。Hello world 123 里 123 单独一块。
    • 再不行就匹配「可选空格 + 非字母非数字非空白」，也就是标点。
    • 空白用负向先行断言：吞掉「除最后一个空格以外的空白」，好让最后一个空格去跟后面的词组成 you 这种常见词元。GPT-2 很喜欢「空格打头的词」。
    • 最后兜底：剩下的空白。

    缩写规则很脏。它写死了 ASCII 撇号；Unicode 弯撇号对不上，会切成另一套。源码注释自己承认：本该加 re.IGNORECASE，好让大写缩写也能合并。没加的后果是 don't 和 DON'T 行为不一致。这些规则还很英语中心，别的语言用不用撇号，会被不一致地切开。

    Python 代码用这条正则切完，每一块内部才允许合并。你可能以为 OpenAI 训练时就是「切块 + 块内 BPE」。并不完全是。同一段空格贴进 tiktokenizer，GPT-2 仍然每个空格都是 220，说明他们另外禁止了空格合并。GPT-2 分词器的训练代码从未公开，放出的只是推理：给定已有 merges，对新文本编码。真实训练比「切完再 BPE」多一些未写明的规则。

    tiktoken，以及 GPT-4 改了什么

    tiktoken 是 OpenAI 官方推理库，pip install tiktoken，没有训练。几行就能拿到 GPT-2 或 GPT-4 的编号。GPT-2 的空格不焊；GPT-4 焊。

    各词表的定义在库里的 OpenAI 公开文件。GPT-2 那条正则和论文/encoder.py 等价，只是写得更快一点。cl100k_base 是 GPT-4 词表，正则改了，特殊标记也多了。词表从约 5 万到约 10 万。

    GPT-4 正则的几处硬变化：

    • (?i:...) 忽略大小写，修掉了 GPT-2 缩写的大小写坑。
    • 空白处理更细，讲座里不逐字符抠。
    • 数字只匹配 1 到 3 位 \p{N}{1,3}，超长数字不会焊成一个巨型词元。这是 GPT-4 算术仍然别扭的根源之一：677 不必是一个词元。

    这些选择几乎没有文档。我们只拿到模式本身。

    GPT-2 的 encoder.py

    文件不长。底部加载 encoder.json 和 vocab.bpe，再构造 Encoder。前者等价于我们的 vocab（编号 → 字节），后者等价于我们的 merges。有这两张表，就能编码和解码。

    另外还有 byte encoder / byte decoder。那是一层串在真正 BPE 外面的实现细节，不深刻，讲座跳过。核心是他们叫 bpe 的函数：循环找下一对该焊的 bigram，整段替换，直到没有能焊的对。算法上就是我们写过的东西，代码比较乱。

    特殊标记：另一路编号，不是焊出来的

    除了字节和合并，还可以插入用来切分数据、给序列加结构的特殊标记。GPT-2 的 encoder 长度是 50257：256 个字节 + 50000 次合并 = 50256，多出来的第 50257 个是 <|endoftext|>。训练时文档与文档之间插入它，当作「上文可以忘掉」的信号。模型得从数据里学会这一点。

    在 tiktokenizer 里，字符串还没写完时，这些字符按普通 BPE 切；一旦完整匹配，突然变成 50256。这不是合并出来的，是编码路径上的特判。encoder.py 里几乎看不见这套逻辑；Rust 版 tiktoken 里有完整的登记与替换。

    基础语言模型用它切文档；微调、ChatGPT 用它切对话。<|im_start|> / <|im_end|> 这类标记圈出 user / assistant。tiktoken 允许你 fork cl100k_base，再登记自己的特殊标记。

    GPT-4 除了 endoftext，还有 FIM（fill in the middle）的 prefix / middle / suffix，来自填中论文，这一讲不展开。

    加特殊标记要做模型手术：嵌入表加一行（通常小随机初始化），最后的分类投影也加一维。从基座模型做成聊天模型时，这是常规操作。

    编码时必须显式允许它们。tiktoken 默认会拒绝字符串里突然冒出来的特殊标记，这是对的：用户提示是攻击者可控输入，不该能偷偷注入「对话结束」。

    作业：自己写到能对齐 GPT-4

    到这里你已经有材料去写一个 GPT-4 分词器。我为此开了 minbpe，并写了 exercise.md，四步堆到能复现 GPT-4 行为。卡住就看测试和源码。

    写完应能对齐 tiktoken：同一句编码得到同一串编号，再 decode 回来。你还可以实现 tiktoken 没有的 train。把 GPT-4 的合并可视化：前 256 是字节，第一次合并往往是两个空格焊成 256。用泰勒·斯威夫特的维基词条（很长，不是因为我是果粉）自己训一份，会看到相似的早期合并（in、空格+t），差别主要来自语料。GPT-4 词表里空白合并更多，说明分词语料里代码大概不少。

    SentencePiece：Llama 那条路

    业界另一套常用库是 Google 的 SentencePiece。Llama、Mistral 等许多模型用它。它能训练也能推理，算法之一就是 BPE。和 tiktoken 的关键差别是操作顺序。

    tiktoken：码点 → UTF-8 字节 → 在字节上合并。SentencePiece：直接在码点上跑 BPE。罕见码点由 character_coverage 决定：不够常见就映射成 UNK；若打开 byte_fallback，则把罕见码点编成 UTF-8，再用词表里预留的 256 个字节词元表示。我认为 tiktoken 干净得多，但这个差别很大。

    SentencePiece 配置极多，历史包袱重。许多开关属于别的算法，比如 shrinking factor 与 BPE 无关。讲座里尽量对齐 Llama 2：从 Meta 放出的 tokenizer 模型用 protobuf 读出选项再抄过来。归一化、小写、压缩空白——前 LLM 时代机器翻译、分类常用；做语言模型我希望尽量别碰原始数据，能关就关。

    它还有「句子」这个概念：训练样本数、最大句长、是否打乱。对 LLM 来说，什么叫一句，不同语言定义不同，原始数据里更是说不清。我宁愿把文件当字节流。

    它也有切数字、切空白这类规则，眯着眼看，相当于 tiktoken 用正则分家。特殊标记方面，UNK、BOS、EOS、PAD 是硬编码的；我的理解是 UNK 必须存在。

    词表 400 的玩具例子：开头是 UNK=0、BOS=1、EOS=2；PAD 设成 -1 就没有；然后（若 byte_fallback）256 个字节词元；然后是合并出的父节点；最后是训练集里见过的原始码点。韩语若不在训练集里：有 byte_fallback 时走 UTF-8 字节（编号还要加上前面特殊标记造成的偏移）；关掉 fallback，整串变成 0，也就是 UNK。各种没见过的东西全挤进同一个 UNK，模型无法区分——所以 Llama 把 byte_fallback 打开是对的。

    空格在可视化里常显示成粗下划线。更关键的是 add_dummy_prefix：在文本前加一个假空格，让句首的 world 和句中的 world 都变成「空格+world」。tiktoken 里 world 和 world 是两个编号，模型得自己学它们相近。Llama 2 也开了这个选项。

    小结：SentencePiece 能训能推，工业上常用；句子长度、UNK 必须存在、码点上 BPE 再回退字节，这些我都不觉得优雅；文档也不友善。要用就对着 Llama 2 的配置抄，并自己把超参数逐项看懂，否则可能默默截断句子。

    词表该设多大

    回到上一讲的 GPT 实现。词表几乎只出现在两处：词元嵌入表（行数 = 词表），以及最后的 LM head（为每个词元打一个 logit）。词表变大，嵌入加行，最后一层多做点积。

    为什么不能无限大？计算更贵；每个词元在数据里更稀，对应向量可能欠训练；单个词元若塞进太长的字符块，一次前向可能消化不了。这主要是经验超参。当时前沿大约在「高几万到十万」附近。

    给预训练模型加词元很常见：聊天微调要加对话结构标记，工具调用再加一批。做法是嵌入表加行（小随机初始化），LM head 加列。可以冻住基座、只训新行，也可以一起训。手术很轻。

    新词元不只是特殊标记：gist tokens

    设计空间比「加几个聊天标记」大。有一篇工作叫 gist tokens：场景需要很长的提示词，每次都编码、都做注意力，很重。他们插入少量新词元，冻住整网，只训这些新嵌入，用蒸馏让模型在「只看见这几个 gist」时行为接近「看见整段长提示」。推理时丢掉长提示，换上这几个编号。这是参数高效微调的一种：不训 LoRA，只训词元嵌入。整类方法够单开一讲，这里只点一下。

    图像、视频、音频也在「分词」

    最近的趋势是：别为新模态改 Transformer 骨架，把图像、视频、音频切成词元，假装它们也是文本编号。早期论文把图像切成整数块，可以是硬词元（强制离散），也可以是软词元（过自编码器瓶颈，不必是整数）。Sora 那篇用 visual patches 谈视频：LLM 有文本词元，Sora 有视觉块，离散词元可走自回归，软词元可走扩散。细节超出这一讲，但「一切皆词元」是同一抽象。

    回过头看那些怪癖

    现在可以回答开头那张清单。

    拼写和字符串操作。字符被焊成长块。GPT-4 词表里有很长的词元，比如 defaultStyle 一类会整段变成一个编号。问「这个词里有几个 L」，模型看见的是一个原子，不是一串字母，数错并不稀奇。让它直接反转 defaultStyle，会搅成乱码。若先要求「把每个字符用空格分开打印」，再反转那张列表，它反而对了——因为你把一个词元拆回了许多字符级词元，任务突然变得可看。

    非英语。不只有模型数据偏英语，分词器也偏。Hello how are you 五个词元，译成韩语可能十五个，膨胀三倍。极常见的问候语「안녕」都可能是三个词元，而 hello 是一个。文本被拉长，窗口更快用完。

    算术。加法是按位的字符级算法，但数字被任意切开。有一篇博文叫 Integer tokenization is insane，系统看了 GPT-2 的四位数：有时一个词元，有时 1+3、2+2、3+1，完全任意。模型能凑合算，是顶着逆风。Llama 2 用 SentencePiece 时选择把数字拆开，部分就是为了减轻这件事。

    GPT-2 的 Python。缩进空格每个都是 220，上下文被空白吃掉。GPT-4 把多空格焊起来，这是分词修复，不只是模型变强。

    看见 <|endoftext|> 就停。让模型打印这个字符串，它会表现得很怪，像是内部把它当成了真正的结束标记。用户提示是攻击者可控输入，按理不该把其中的特殊标记解析成真词元；一旦 encode(..., allowed_special=...) 把用户文本里的这段放行，就会变成攻击面。想折腾模型，可以试试塞特殊标记。

    trailing whitespace。在 Playground 用 GPT-3.5 Turbo Instruct 这种补全模型，写「Here's a tagline for an ice cream shop」能正常续。若在末尾多打一个空格再提交，API 会警告：文本以空白结尾，表现会变差。原因：GPT 系喜欢把空格焊进下一个词， o 是词元 8840，不是「空格」加「o」。你在末尾先放一个孤立的 220，等于把下一个词元撕成两半，分布外了。模型几乎没见过这种「词元刚起了个头」的上下文。

    同类问题还有「半截长词元」。defaultStyle 在训练里几乎总是一个整体；你只输入前半截，模型可能立刻吐结束符，或触发乱七八糟的安全策略。tiktoken 的 Rust 代码里搜 unstable，有大量未文档化的「不稳定词元」处理。补全 API 真正该做的，可能是在字符级搜索高概率延拓，而不是在半截词元后面硬接下一个整词元。这整坨都来自分词，以后或许能单开一讲。

    SolidGoldMagikarp。有人把词元嵌入聚类，发现一簇古怪字符串：SolidGoldMagikarp、StreamerBot 之类。问模型重复这些词，会得到回避、幻觉、甚至骂人——安全对齐像被打穿。SolidGoldMagikarp 是 Reddit 用户名。推测是：分词器训练集里 Reddit 很多，这个高频用户名被焊成了专属词元；后来语言模型的训练集里没有这批 Reddit，该词元从未被采样，嵌入表那一行从随机初始化起从未更新，等价于未分配内存。测试时一激活，Transformer 吃到未训练向量，行为未定义。分词语料和模型语料不一致，就会在词表里留下这种地雷。

    YAML 对 JSON。同一份结构化数据，JSON 往往更吃词元，YAML 更省。讲座里一份对照大约 116 对 99。按词元计费、按上下文付钱时，密度就是成本。多在 tiktokenizer 里量一量。

    收场建议

    这一讲又干又烦，我自己也不喜欢这层。但不要敷衍：暗坑、安全问题、把未分配内存插进模型，都在这里。能取消分词的人，将得到不朽荣耀。前面那篇无分词论文是一个方向，希望后来者更多。

    眼下做应用：若能复用 GPT-4 词表，就用 tiktoken，推理又快又干净。我也更喜欢 OpenAI 那种字节级 BPE。若必须自己训词表，目前工业上仍常走 SentencePiece 的 BPE；我不喜欢它在码点上合并、不喜欢 byte fallback 的形态、不喜欢那一百万个开关——抄错一个最大句长，就会悄悄裁句子。对照 Meta 的配置，把超参数和源码过一遍。即便设对了，算法上我仍觉得不如字节级 BPE。理想状态是「tiktoken 的推理 + 能训练」，当时还不存在。minbpe 是这个理想的 Python 实现，还不够快。也许以后会有更干、更细的续集。希望有用，再见。
