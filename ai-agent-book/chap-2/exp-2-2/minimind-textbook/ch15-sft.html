第四部 · 训练

第 15 章 · 对话模板与监督微调

预训练会接龙，还不会当助手。监督微调（SFT）继续做下一个词预测，但文本换成「用户 / 助手」模板，并且只在助手要说的那些词元上算损失。

预训练和微调的相同与不同

相同：还是交叉熵，还是同一个 MiniMind-3，还是 AdamW。不同有三处：

  1. 初始权重。从 pretrain_768.pth 加载，而不是随机初始化。学习率降到 1e-5 量级，免得把已经学到的语言知识冲掉。
  2. 数据。jsonl 里是 conversations 列表，角色为 user / assistant / system / tool。
  3. 损失掩码。用户说的话、系统提示、填充，标签都是 -100。只有助手回复（以及它的结束符）产生梯度。

若对用户文本也算损失，模型会把「模仿用户怎么提问」当成目标，助手风格就不稳。掩码是微调里最关键的工程细节。

如何只给助手位置打标签

官方的办法是在编号序列里扫描「助手段开始」和「段结束」两串特征编号：

  • 开始：把 bos_token + "assistant\n" 编成的那一小段 id（bos_id）；
  • 结束：把 eos_token + "\n" 编成的 id（eos_id）。

从每个开始标记之后，到对应结束标记（含结束符）之前，把 labels 设成与 input_ids 相同；其余保持 -100。多轮对话就有多段助手回复，循环扫描即可。

请用一条两轮对话打印 tokenizer.decode：凡是用户字，对应 label 应是 -100；助手字应等于该位置的 input id。

SFT 数据上官方还做了两件随机事

  • 约 20% 的样本若本来没有 system，就随机插一句系统提示（「你是 minimind……」这类）。
  • 若模板里出现空思考块，约 80% 概率把它删掉，让模型见过「直接回答」和「带着空 think 标签」两种表面形式。

工具调用样本（conversations 里带 tools）不做这些随机改写，以免拆坏 JSON 结构。当前主线的 sft_t2t / sft_t2t_mini 已经混入工具调用，因此通常不必再单独训一轮 toolcall。

微调仍然可以灌知识

不要把 SFT 理解成「只学格式」。MiniMind 主线 SFT 数据到 14GB 量级时，它更像带目标的继续训练：既对齐对话格式，也继续压入知识和工具使用习惯。小数据的身份 / 医疗 LoRA 才是「尽量不改通用能力、只补一块」——见第 17 章。
