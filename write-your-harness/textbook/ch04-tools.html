第二部 · 零件

第 4 章 · 六种工具，不是六十种

工具是模型伸向世界的手。手太少，活干不成；手太多，说明书本身就把上下文撑满。这一章把六件套做对，并看清「只给 bash」为什么也能赢。

这一章只要记住

编码助手的最小工具箱几乎总是：读、写、改、找文件、搜文字、跑命令。工具可以更少（只给 bash），很少需要更多。少，是为了让模型把注意力放在任务上，而不是放在「我该选哪一个专用工具」上。

六件套是干什么的

假设任务是「add(2,3) 应该等于 5」。模型通常会这样伸手：

  1. glob：工作区里有哪些文件？先摸清现场。
  2. read：打开 calc.py，看见 return a - b。
  3. edit：把那一行换成 return a + b。
  4. bash：跑测试，确认真的过了。

另外两件是备用：write 用来新建文件（测试文件、补丁稿）；grep 用来在很多文件里搜一个函数名，比逐个 read 便宜。

工具人话为什么不能互相替代干净
read看一个文件（带行号）edit 需要精确旧字符串；行号让模型好引用
write整文件覆盖 / 新建适合从零创建；拿它改大文件容易把没动过的部分弄丢
edit外科手术式替换旧字符串必须几乎唯一，防止误伤
glob按名字找文件不知道路径时的入口
grep按内容找文字知道符号、不知道在哪个文件
bash跑测试、看 git diff文件系统工具做不到「执行一段程序」

工作区：工具能摸到的世界边界

打开 tools.py 会看到 Workspace。它记住一个根目录，所有路径都相对这个根。

这不是操作系统沙箱。它挡的是「糊里糊涂读到仓库外面」；挡不住 bash("curl http://evil")。第 12 章 Codex 才在 OS 层动手。现在先把路径关好——大多数教学事故来自相对路径 ..，不是来自黑客。

另一极：只给 bash

mini-swe-agent 的默认 agent 几乎只暴露一个工具：执行 shell 命令。模型要读文件？它自己写 cat calc.py。要改文件？自己写 sed 或 here-doc。要搜？rg。

这看起来「更原始」，在评测里却很强，原因有三条：

  1. 说明书极短。上下文省给代码和错误信息，而不是六十个工具的 JSON。
  2. SWE-bench 现场本来就是带 git 和测试命令的 Linux 环境。bash 是这个世界的母语。
  3. 独立子进程：每次命令都是一次新的 subprocess.run，不保留「上一次 cd 到了哪」。状态只存在磁盘和 git 里，评测可复现。

生活比喻

六件套像给厨房配刀、锅、铲、勺。只给 bash 像只给一双手：慢一点，但不会发生「我该用哪把专用刀」的选择瘫痪。考试（评测）时，选择越少，不同模型之间越公平。

miniharness 走六件套，是因为教学要看见每种工具的失败模式（edit 不唯一、glob 太宽、bash 超时）。写评测脚手架时，你可以只留 bash——第 8 章会回来。

先别管 · 原生调用 vs 文本里抠 JSON

我们走「原生 tool calling」：模型 API 单独返回 tool_calls 字段。另一种做法是让模型在正文里写出 {"tool": "read", ...}，再用正则去抠。后者在模型不支持原生调用时有用，也更脆（模型多写一个逗号就解析失败）。mini-swe-agent 两种都能接。你的循环应把「解析出 ToolCall 列表」关在模型适配层，不要让正则漏进 run_agent。

自测

  • 模型 read 之后把 3| return a - b 整行拿去 edit，会发生什么？
  • 为什么「工具越多，agent 越强」常常是错的？
  • Workspace 挡得住 bash("rm -rf /") 吗？
自测答案
  1. 文件里没有带 3| 的那一行，edit 命中 0 次，返回错误。模型需要丢掉行号再试。
  2. 每多一个工具，说明书就占上下文，模型还要多做一次选择。评测里，选择本身会变成噪声。
  3. 挡不住。Workspace 只管文件路径解析。危险命令要靠第 6 章的拒绝列表和第 12 章的 OS 沙箱。
