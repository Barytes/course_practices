这一章只要记住

循环只有一个正常出口：模型这一轮没有发出 tool_calls。护栏把你踢出去是另一个出口。打印、压缩、插件都是可插拔的旁路——第一遍默写可以假装它们不存在。

模型在循环里只是一个插座

循环不关心模型是真人、是云端 API，还是一段预先写好的剧本。它只要求对象有一个方法：

实验里我们用 ScriptedModel：一部录音机。你预先写好每一轮它会说什么、要调什么工具，它按顺序播放，不联网。这样测试 harness 时，失败一定是循环或工具写错了，而不是「模型今天心情不好」。

手算：消息列表怎么长出来

工作区里有一个文件 a.txt，内容是 hello。用户问：「文件里写了什么？」剧本是：先 read，再用人话回答。

开始之前

第一次 complete：剧本第 1 拍，点名 read。循环必须先把这条 assistant 追加进去，再执行工具——否则轨迹里会丢「它当时到底要了什么」。

第二次 complete：模型已经看见第 2 行，剧本第 2 拍只有人话。

一共两次模型调用、一次工具。若第 2 次模型又 read 同一路径——循环仍然会照做。笨不笨不是循环的事；第 6 章的指纹才会喊停。

代码怎么对上原理

  • append(reply) 在执行工具之前：即使工具稍后失败，轨迹也留下点名。
  • 一次 assistant 可以带多个 tool_calls。我们按列表顺序执行。有的生产系统会并行——那是取舍，不是正确性。
  • tools.run 应当返回字符串，包括 "error: …"。不要把异常甩出循环。模型需要看见错误才能改主意。
  • tool_result(call, result) 会带上 call.id，对应第 1 章的 tool_call_id。

文件里多出来的那些行是旁路

真实的 run_agent 在每次问模型之前，可能先压缩旧观察、先让插件改一改 messages；每跑完一个工具，也可能让插件改一改观察；全程往 events 里塞小纸条。第一遍请把它们当成「收音机里的广告」：

  • 压缩 → 第 5 章
  • 护栏 → 第 6 章
  • 插件和事件 → 第 10、11 章

和 mini-swe-agent 的同构

打开 default.py，你会看到另一种拼写：

query 就是 complete；execute_actions 就是跑工具并追加观察。结束条件写成 exit 消息，是因为评测需要「提交 / 超时 / 格式错误」这些显式出口。我们用 stop_reason 字符串做同一件事：completed 或 repeat_loop 或 step_limit。

常见卡住

  • 把「流式输出」（一个字一个字蹦出来）当成循环的一部分。——那只影响界面好不好看。循环关心的是完整的一条 assistant 消息。
  • 在循环里直接 print 当日志。——可以，但最好像我们一样 append 到 events。产品级要把「能看见」做成一等公民，见第 11 章。
  • 剧本用完了 ScriptedModel 还在被问。——它会返回「(script ended)」。测试里请把剧本写够，或靠步数上限停。

自测

  • 模型一轮里调用了 read 和 grep。这一轮 complete 几次？整个任务至少还要再 complete 几次？
  • 为什么 ScriptedModel 对实验比真 API 更重要？
  • 工具抛了异常，循环应不应该让 Python 直接崩溃？
自测答案
  1. 这一轮 complete 一次，顺序执行两个工具，然后再 complete 至少一次（看它还要不要工具）。
  2. 循环和工具的测试必须确定。真模型会改主意，你会分不清是 harness 坏了还是模型今天心情不好。
  3. 不应该。要变成观察字符串写回去。崩溃等于模型失聪。
