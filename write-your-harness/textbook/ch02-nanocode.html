这一章只要记住

1rgs/nanocode 是一份单文件、零依赖的编码助手缩小版。骨架只有四拍：收用户输入 → 问模型 → 若有工具就执行并写回 → 再问。没有沙箱，没有压缩，没有插件，没有评测。这不是缺陷，是标本该有的空白。

在文件里用搜索定位这几个名字：def read、TOOLS、def call_api、keep calling API、input(。搜到了，结构就齐了。

250 行里的七块

  1. 六个工具函数：read / write / edit / glob / grep / bash。编辑要求旧字符串在文件里只出现一次，除非显式说「全部替换」。第 4 章会用手算说明为什么。
  2. 工具表：名字 →（描述, 参数草图, 函数）。同一张表干两件事：生成给模型看的说明书，以及真正分发调用。改工具时只改这一张表，不容易漏。
  3. call_api：用 Python 自带的 urllib 发网络请求，把「到目前为止的 messages」和「工具说明书」一起寄出。不依赖第三方 SDK。
  4. 内层循环：源码注释就是定义——一直问 API，直到没有 tool 调用。这就是第 3 章要默写的东西。
  5. 外层循环：读你在终端里打的字。/c 清空消息（等于失忆），/q 退出。
  6. 系统提示：一句「Concise coding assistant. cwd: …」。没有 20 页的宪法。模型变强之后，短提示往往够用；长提示会占上下文、还会在发版时偷偷变。
  7. 打印：给人类看的颜色和缩进。不是循环的一部分，是司机仪表盘。

这份说明会随每一次 complete() 寄给模型。说明书越长，每一轮越贵——所以工具不是越多越好。这是后文「六件套 vs 只给 bash」的伏笔。

先别管 · 两家 API 的信封不同

nanocode 走 Anthropic 那种 Messages 接口：工具结果常常塞在 role=user 的一组 tool_result 块里。OpenAI 兼容接口更常见独立的 role=tool。miniharness 用后者，因为课程里的客户端多半是 OpenAI 形状。信封变了，循环没有变：有工具就执行并追加，没有就停。

自测

  • 外层循环和内层循环，哪一层在「用户还没说话」时空转等待？
  • 为什么 edit 要求旧字符串唯一？
  • nanocode 把工具结果放进另一种信封。若你改成 role=tool，循环变了吗？
自测答案
  1. 外层。内层只在「已经有用户消息、正在干活」时转。
  2. 避免一次替换打中文件里多处同名片段，把不该动的地方改坏。这是工具设计，不是模型智商问题。
  3. 消息的 JSON 形状变了，循环没有变：还是「有工具就执行并追加，没有就停」。
