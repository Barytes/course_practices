第 15 章 · 发布即过时：以后怎么自学

把这本书从收藏夹里拿掉。留下命令、留下问题清单、留下「版本号必须带日期」的强迫症。

这一章只要记住

nanocode 和 mini-swe-agent 几乎冻结，当标本。pi / opencode / codex / dsh 当时间线：全量拉 releases，让现在的模型帮你梳理，有疑问跟到 commit 和 issue。不要用下一本电子书替换这一步。

为什么书会死，循环不会

第 0 章说过一次，这里用操作手册再说一次。会过时的是：类名、包名、默认是否开启某功能、某家沙箱的具体系统调用表。不太会过时的是：

  • 有工具就执行并写回，没有就停。
  • 观察必须进上下文，磁盘真相 ≠ 模型真相。
  • 评测要用瘦架子，分数才像模型的分数。
  • 高风险动作需要硬约束，提示词不算约束。
  • 上下文按轮数变贵，压缩会打乱前缀缓存。

自学的目标不是「把 2026 年 9 月的 dsh 背下来」，是「下一次 release 你知道该问什么」。

先把时间线拉回来

匿名的 GitHub HTTP 接口经常直接 403。命令会先试 gh api，再退回带 token 的请求。拉下来的是各仓库最近几条 release 的标题和说明，不是全文源码。

写到哪里

文件miniharness/watch.py
符号snapshot、render
怎么跑python -m miniharness watch

怎么读一份 Release（比通读源码便宜）

  1. 先找破坏性变更。改名、删 API、默认行为反转。dsh 0.1.6-alpha.1 把某条会话事件改名、PTC 包改名——这种句子比 20 个新功能值钱。
  2. 再找取舍声明。「我们删了 visual UI，因为没人用还难维护」（mini v2）。这是维护成本投的票。
  3. 把句子跟到 PR / commit。看测试改了什么，比看宣传句更接近真实约束。
  4. 最后才看新功能清单。功能是广告；约束才是架构。

没有 Release 的仓库怎么读

nanocode 几乎没有 Release。那就看 commit 时间线：是不是真的冻住了？某天突然复活，本身就是信号。issue 里搜 wontfix、by design，能看见他们后悔什么、故意不做什么。

不要用书籍研究 AI 和 Agent

书能做的，是把循环放进你的手指，把问题清单放进你的嘴边。书不能做的，是代表三个月后的 opencode，或明年的某种 PTC。去年的编排库教程、开源两个月的「全书」，都在尝试后一件事。那件事性价比甚至不如直接问现在的模型——它至少连着现在。

你若还想「收藏一本 Agent 电子书」，把 miniharness watch 的输出收藏进去。那是活的。这一章的 HTML 不是。

常见卡住

  • watch 返回 403。——登录 gh，或设 GITHUB_TOKEN。不要为此去抄一篇「GitHub API 教程」进教材。
  • 想等作者把书更新到最新版本。——不会有这一天。书的工作在第 3 章结束时已经完成一大半。

自测

  • 一份 release 同时宣布「新主题」和「默认工具表改了」。你先读哪一句？
  • 为什么要把版本号和日期绑在一起写？
自测答案
  1. 默认工具表。它改的是所有人的上下文和评测可比性。主题是皮肤。
  2. 「v1.18」单独出现会假装自己永远正确。写下「v1.18.31（2026-09-14）」是在提醒读者：过了这一天，以仓库为准。
