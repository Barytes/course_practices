第 13 章 · deepseek-harness：万物皆插件

如果 pi 是「核心很小、扩展挂旁边」，dsh 把这句话做到尽头：循环自己也是插件。这一章会把手伸进启动树、事件日志、工具管道和 PTC。它还处于开发者预览，破坏性变更是特性，不是丑闻。

这一章只要记住

仓库 deepseek-ai/deepseek-harness（快照 dsh-v0.1.6-alpha.1，2026-09-15；公开 GitHub 的 Pull Requests 页是空的，内部 merge 编号另算；仓库 2026-08-13 才公开，master 已有约 1.7 万次提交）。先读 docs/architecture.md。不要背包名。带走两件事：会话日志是唯一真相；模型可以一次写一段程序来组合工具。最重要的三次投票是：事件溯源会话、可重建请求、PTC。

没有特权核心

pi 还保留一块「这就是循环」的核心。dsh 更绝：模型适配器、工具表、会话日志、agent 循环、界面，全是插件。你扩展产品的方式是在旁边再挂一个插件，而不是给「核心」打补丁。卸载时，它注册过的效果要能撤掉。

生活比喻

pi 是改装空间很大的车架，螺丝孔是厂家打好的。dsh 是实验室底盘：连车架本身也是用快拆螺丝拼起来的。换悬挂很爽；说明书上的螺丝编号每周都会改一版。

启动是一棵树：profile 列出要叠的 bundle，再叠用户的 cordis.patch.yml。同一套代码可以长出网页、无头、SDK、ACP。界面和研究用的最小模式能共享循环——换的是叠了哪些插件。

他们把这套插件系统叫做 Cordis（源码 vendored 进仓库，为了可审计、可打补丁、钉死版本）。名字会过时，结构不会：共享上下文、类型化事件、可逆效果。

架构：日志在前，投影在后

miniharness 的 messages 数组既是真相也是请求。dsh 把这两份拆开：日志是源，请求是投影。

一轮 turn 里可以有多步 step。工具走完整管道：tools/pre-execute → 单调护栏 → tools/execute → tools/post-execute → tools/result。PTC 的 run_code 和它里面每一次 tools.read 都走同一条管道——不能因为「这是一段程序」就放行。

打开哪几个文件（快照 dsh-v0.1.6-alpha.1）

  • docs/architecture.md —— 宪法。先读这一份。
  • docs/tool-execution-pipeline.md —— 一次工具从点名到写回的水管。
  • .agents/notes/implemented/feature/2026-06-15-ptc.md —— PTC 为什么存在、权限为什么不放宽。
  • docs/cordis-primer.md —— 插件树的最小心智模型。名字会过时，结构不会。

公开 GitHub 的 PR 页是空的。投票在这些笔记里。包名每周都可能改，问「行为挂在哪条缝上」。

启动是一棵树，不是一个入口

profile 列出要叠的 bundle，再叠用户的 cordis.patch.yml，再叠家目录的，再叠 --patch。每一层按 id 整行替换或插入。web / headless / sdk / acp 共享 dsh-base（模型、工具、持久化、沙箱、审批）。sdk-minimal 故意不叠它，作为对照实验。

所有 Node 应用都必须从 dsh CLI + 具名 profile 进。多一个可执行文件就是多种启动真相。仓库里有脚本专门拒绝旁路入口。

web 配置可热更新；headless / sdk / acp 启动时叠死——替换一个正在干活的一次性进程的依赖，会让生命周期作废。0.1.6-alpha.1 更诚实：热更新不再假装事务回滚，解析失败留旧配置，插件激活失败可能部分生效。

日志是源，请求是投影

miniharness 的 messages 数组既是真相也是请求。dsh 把这两份拆开。append-only 的 SessionEvent 是唯一真相。deriveMessages() 从日志折出模型历史，从不另存一份。

运行时断言：寄出的请求必须能从日志字节级重建。对不上就大声失败。插件若要改已有消息内容，必须注册纯函数投影，重放时还能得到同一份——禁止私下改内存再寄出。

活的字走短暂的 agent/assistant-stream。落盘的是结算后的完整 assistant/message。失败、重试、取消走进 assistant/attempt，不进模型历史。结算前 kill -9，不得假装有过成功回复。

JSONL 分代：v0 叫 session.jsonl，vN 叫 session.vN.jsonl，可 zstd。已提交路径永不改名删除。打开时选数字最大的一代，需要的话沿相邻迁移链走到当前逻辑格式。迁移是单向出版下一代，不是原地改写。

turn 和 step：欠债还清才关门

一步 step = 一次模型请求 + 它点名的工具。一轮 turn = 零步或多步：第一笔输入被认领时打开，什么都不欠了才关闭。

输入进同一只收件箱。有的消息立刻叫醒循环；注入的上下文要等下一则真正唤醒的消息——避免鬼上下文。重试不重复装配，也不再跑 agent/pre-step。

空的系统提示必须清掉旧节点。否则模型会看见上周的人设。能缓存前缀的路由，可以把非空更新接在后面；不能的，就在第一个系统节点上合并。

工具管道：政策不进循环肚子

点名先落盘 tool/call，界面先画一张 pending 卡，然后：

  1. tools/pre-execute 瀑布：钩子、权限、沙箱。可放行、拒绝、或 ask。
  2. ask 走 ctx.approval 一次性提问。答不上来 = 拒绝。
  3. 单调护栏：只许 deny 或弃权，不许改身份。
  4. tools/execute 瀑布包着真正的 execute()：超时、重试、指标。
  5. 文件系统写/改意图走 fs/* 事件，读-改检查不进通用瀑布。
  6. tools/post-execute：接受、挡住、替换、附加上下文。
  7. 定义自己的 finalizeContent 是最后一次只改内容的机会。
  8. tools/result 同步通知冻结后的权威结果，再落盘。

PTC 子调用带着父 token 再走同一条水管，记录 tool/ptc-dispatch，拒绝变成程序里的绑定错误。子调用不得往外塞 additionalContexts——否则会拆开父调用和父结果的相邻关系，投影会乱。

并发：工具自己声明是否并发安全，fail closed。PTC 子调用按提交序启动，可并行到上限，排他调用当屏障。早期的「先串行占位」已经被后来的笔记替换。

PTC 的三层，不要揉成一层

呈现模式
native / ptc / both。这是工具注册表的配置，不是另一种循环。both 可能把模型搞糊涂。
运输层
保留的 run_code({ code, description })。它在限制名单外面，以免有人把 PTC 的唯一入口过滤掉。
运行时缝
ctx.ptcRuntime 只知道程序和具名异步绑定，不知道工具表。换 Python 后端是换提供者，不是改循环。

SDK 从同一张可见工具表生成，按字典序排，求字节稳定。说明书和真正注册的工具必须是同一张表——否则模型会调不存在的函数，或绕开已有的。

沙箱升级用「只放宽这一次程序」的审批，嵌套 dispatch 仍挂原来的 Agent 和 Session。失败的程序不会被暗中重放：前面的副作用可能已经提交。

先别管

Cordis 的 ctx 键名、JSONL 第几代、PTC 包名、worker-thread 还是独立进程。预览期的日常就是这些在变。盯三件事：日志是源；每一次底层工具仍走管道；启动只有一个入口。

教学版 PTC 对到哪里

前面已经用手算走过原生 vs PTC。下面只对 miniharness 那 40 行。

写到哪里（教学版 PTC）

文件miniharness/ptc.py
符号PtcToolbelt、run_code、sdk_stub
怎么跑python tests/test_miniharness.py PtcTests

代码怎么对上原理

  • PtcToolbelt.schemas() 只暴露 run_code。循环以为世界上只有这一个工具。
  • run_code 用 Python 的 exec 跑模型写的脚本，并把 tools.read 等函数指回原来的 Toolbelt。路径笼子仍然有效。
  • sdk_stub() 生成那份「你能调用哪些函数」的说明书。真系统会把它放进 system 提示。
  • exec 不是沙箱。教学版只为了让你摸到「表面是一个工具」。真隔离看 dsh 的代码运行时和 Codex 的 OS 沙箱。

先别管

2026-09-15 的 release 还在改 PTC：包名、是否独立进程、环境变量清不清理、内存上限。预览期的日常就是这样。你若把上周的配置抄进书当标准，书已经在撒谎。盯「独立进程 + 权限仍走底层工具」这个方向即可。

自测

  • PTC 少了哪些轮次？没少什么约束？
  • 为什么 SDK 说明书必须和真正注册的工具一致？
  • miniharness 的 exec 能代替 Codex 沙箱吗？
  • 为什么公开 GitHub 上 PR 数为 0，教材还要写「历史投票」？
  • 一条 assistant/attempt 会不会进下一轮模型历史？
  • PTC 子调用为什么不准当场往外塞 additionalContexts？
自测答案
  1. 少的是「每调一次宿主工具就问一轮模型」。不少的是每一次底层 read/edit/bash 仍要过路径和护栏。
  2. 模型按说明书调用不存在的函数，程序会报错；说明书少写了已有工具，模型会绕远路或放弃。两边必须是同一张表生成出来的。
  3. 不能。exec 跑在同一进程、同一用户权限里。它只是教学用的组合器。
  4. 因为他们的投票写在架构笔记和内部 merge 编号里，不写在 GitHub Pull Requests 页。读这个仓，releases 和 .agents/notes 比 PR 页更接近真相。
  5. 不会。attempt 是失败/重试/取消的结算，给人和遥测看。模型只看见成功的 assistant/message。
  6. 会拆开父 run_code 的 call 和 result 的相邻关系，投影和重放都会乱。上下文要等外层结果写完再 FIFO 追加。
