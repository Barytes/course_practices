第 10 章 · pi：可扩展的极简生产级

从这里起，教材不再给你「标准实现」。pi 证明一件事：核心循环可以保持能读完，产品功能靠旁边的扩展长出来。版本会变；这个分界不太会变。

这一章只要记住

仓库 earendil-works/pi（快照 v0.85.1，2026-09-05；GitHub Search 于 2026-09-16 计 3170 条 PR、979 条已合并）。先看四个包：pi-ai、pi-agent-core、pi-tui、pi-coding-agent。核心小，扩展大，是设计，不是没写完。最重要的三次投票是：会话树（v0.31）、hooks+tools 合成 extensions（#454 / v0.35）、包管理与热加载（#645 / v0.50）。

第四部是「带着问题去读别人的仓库」。循环还默写不出来，请先回第 3 章。下面每个概念都对照 miniharness 里已经有的那道缝。

先讲人话：为什么要把车架拆开

nanocode 把循环、工具、打印塞进一个文件，扫起来痛快，改起来疼：想加「危险命令先问人」，只能去改那唯一的 while True。pi 的回答是把程序拆成几块积木：

生活比喻

自行车的车架（循环）保持很轻。灯、货架、铃铛全部用螺丝挂上去。换灯不必焊开车架。pi 把这件事做到日常能用的程度：你真的会拿它当编码助手，而不是只拿它当标本。

作者 Mario Zechner 在 2025-11-30 的长文 What I learned building an opinionated and minimal coding agent 里写得很直：他讨厌核心系统提示和工具在每次发版时偷偷变；讨厌闪烁的全屏界面；讨厌上下文里被塞进界面都看不见的东西。拆包就是对这些讨厌的工程回答。

架构：四层，外加后来长出来的包

下层不知道上层。pi-ai 零依赖循环；pi-agent-core 不知道 TUI。这就是「换灯不必焊开车架」。

包人话miniharness 里像谁
pi-ai怎么跟各家模型说话；换模型时思考痕迹怎么翻译model.py
pi-agent-core循环、工具、事件、中途加话、中止loop.py + plugins.py
pi-tui终端里怎么画，尽量不抢系统滚动cli.py 的打印（婴儿版）
pi-coding-agent焊成能天天用的 CLI，并开放扩展整包

会话落盘是 JSONL 树：每条记录有 id / parentId。当前叶子往根走，就是模型这一轮该看见的路径。压缩、换模型、扩展私货，都是树上的一种节点，不是另开一份隐秘名单。

默认工具只要四件：read / write / edit / bash。系统提示刻意压在大约一千 token 以内。AGENTS.md 分层读入。作者的原话是：模型已经被 RL 训练到知道 coding agent 是什么，不必再塞一万 token 的说明书。

三条仍然有效的取舍（读源码时带着问题）

1. 给应用看的消息 ≠ 给模型看的消息

界面可能需要「正在输入」「这条工具被你点了拒绝」。这些盒子不该原样塞进模型——又贵，又会教坏模型。pi-ai 允许工具返回两份：output 给模型，details 给界面。会话树上还有 custom 条目：display: true 可以画出来，却不必进 LLM。

miniharness 几乎把两份名单做成同一份。一旦你做界面，就需要这条缝：第 7 章的 events 已经是萌芽，before_model 钩子可以改寄出前的 messages。

2. 事件是给界面的 API

不要在循环肚子里写 print。turn_start / tool_execution_* / turn_end 广播出去，界面、日志、遥测都当听众。我们的 EventLog 是婴儿版。

3. 核心故意不做的功能，后来有的做成了扩展，有的爬进了默认

长文列的「不做」：待办、plan、MCP、后台 bash、子 agent、内置权限。2026 年的仓库更丰富——压缩进了核心，全屏 TUI 变成可切换，包管理进了 CLI。权限和 MCP 仍然不进核心。

正确动作：打开最近的 release，看他们后来把哪些「故意不做」又做了，以及做成了扩展还是默认开启。默认开启就会改变所有人的上下文，这正是作者当初讨厌某些产品的点。

pi-tui 的关键一票

两种终端界面：全屏抢终端（早期 Amp / opencode，以及 Codex 的 Ratatui），以及写在普通滚动缓冲里、只重绘脏行（pi 的默认，也是 Claude Code 那类）。后者保留系统搜索、选中、滚动；代价是超长会话要比对更多行。

v0.84.0 加了运行时全屏模式。这不是「长文作废」，是「默认仍是滚动缓冲，全屏变成灯」。选的时候问：我的用户是不是还把终端当日志看？

教学缝：三只钩子

写到哪里

文件miniharness/plugins.py
符号before_model、after_tool、on_event
怎么跑python tests/test_miniharness.py PluginTests

测试里有一个 Clip 插件：after_tool 把观察剪成 5 个字符加省略号。模型下一轮看见的就是剪过的版本。这就是「不改 loop.py，也能改循环行为」。

生产级的扩展还能注册命令、快捷键、主题、新工具。教学版只留三只钩子。钩子少是优点：你能说清楚每只钩子在哪一拍触发。

先别管

TypeScript 包名、扩展清单、chord 的 RPC、会话中途换模型时思考痕迹怎么序列化——这些会改。你要带走的是分界：循环保持能读完；产品功能挂在钩子上；默认上下文里每多塞一件东西都要有人负责。

读这个仓库时问什么

  • 新功能进了 core 还是 extension？进了 changelog 的 Breaking 还是 Added？
  • 工具执行前的钩子能不能挡住一次 bash？被挡住的结果如何回到模型？
  • 换模型时，思考痕迹怎么交给下一家？（上下文交接）
  • 最近一次「故意不做」被做成默认了吗？v0.84 的全屏是一个现场。

自测

  • 为什么「待办清单做成默认开启」会惹作者生气？
  • miniharness 的 after_tool 改的是磁盘，还是模型下一轮看见的字符串？
  • #454 和 #645 各解决了扩展面上的哪一个问题？为什么要分成两次发版？
  • v0.84 加了全屏 TUI，长文是不是作废了？
自测答案
  1. 它会占用每一轮的上下文，所有用户都付钱，包括根本不用待办的人。做成扩展，需要的人自己挂。
  2. 只改观察字符串。文件该怎么改还是怎么改。下一轮模型看见的是剪过或改过的汇报。
  3. #454 把「有几种插头」收成一种。#645 把「插头怎么分发、怎么热加载」做成包。先统一概念，再做市场；反过来会把两套旧 API 都带进包管理器。
  4. 没有。默认仍是滚动缓冲。全屏是可切换的灯。取舍还在，只是菜单上多了一盏灯。
