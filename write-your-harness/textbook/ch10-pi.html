生活比喻

自行车的车架（循环）保持很轻。灯、货架、铃铛全部用螺丝挂上去。换灯不必焊开车架。pi 把这件事做到日常能用的程度：你真的会拿它当编码助手，而不是只拿它当标本。

三条取舍（读源码时带着问题）

1. 给应用看的消息 ≠ 给模型看的消息

界面可能需要「正在输入」「这条工具被你点了拒绝」这类通知。这些盒子不该原样塞进模型的上下文——又贵，又会教坏模型。pi 的做法是：应用侧有一份更丰富的名单；真正寄出之前，先修剪、再翻译成模型认识的形状。

miniharness 几乎把两份名单做成同一份。一旦你做界面，就需要这条缝：第 7 章的 events 已经是萌芽，before_model 钩子可以改寄出前的 messages。

2. 事件是给界面的 API

不要在循环肚子里写 print。turn_start / tool_execution_* / turn_end 这样的小纸条广播出去，界面、日志、遥测都当听众。订阅者按注册顺序等待。我们的 EventLog 插件是婴儿版：把小纸条收进列表，测试里能断言「工具确实跑完了」。

3. 核心故意不做的功能

早期 pi 明确不做：内置待办清单、计划模式、MCP、后台 bash、子 agent。理由是「我不需要就不做，做了就会污染默认上下文」。2026 年的仓库已经更丰富——所以你不能背那篇文章当现状。

正确动作：打开最近的 release，看他们后来把哪些「故意不做」又做了，以及做成了扩展还是默认开启。默认开启就会改变所有人的上下文，这正是作者当初讨厌某些产品的点。

教学缝：三只钩子

写到哪里

文件miniharness/plugins.py
符号before_model、after_tool、on_event
怎么跑python tests/test_miniharness.py PluginTests

测试里有一个 Clip 插件：after_tool 把观察剪成 5 个字符加省略号。模型下一轮看见的就是剪过的版本。这就是「不改 loop.py，也能改循环行为」。

生产级的扩展还能注册命令、快捷键、主题、新工具。教学版只留三只钩子。钩子少是优点：你能说清楚每只钩子在哪一拍触发。

pi-tui 的关键一票

两种终端界面：全屏抢终端（Codex 那类），以及写在普通滚动缓冲里、只重绘脏行（pi）。后者保留系统搜索、选中、滚动；代价是超长会话要比对更多行。没有普适赢家。选的时候问：我的用户是不是还把终端当日志看？

先别管

TypeScript 包名、扩展清单、会话中途换模型时「思考痕迹」怎么序列化——这些会改。你要带走的是分界：循环保持能读完；产品功能挂在钩子上；默认上下文里每多塞一件东西都要有人负责。

版本会动

包名从 @mariozechner/* 迁到 @earendil-works/*，仓库从 pi-mono 迁到 earendil-works/pi。若有教程还在写旧路径，那就是「发布即过时」的现场。以 GitHub 为准。

自测

  • 为什么「待办清单做成默认开启」会惹作者生气？
  • miniharness 的 after_tool 改的是磁盘，还是模型下一轮看见的字符串？
自测答案
  1. 它会占用每一轮的上下文，所有用户都付钱，包括根本不用待办的人。做成扩展，需要的人自己挂。
  2. 只改观察字符串。文件该怎么改还是怎么改。下一轮模型看见的是剪过或改过的汇报。
