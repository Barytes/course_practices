第二部 · 零件

第 5 章 · 上下文为什么会变贵

循环每转一圈，都要把到目前为止的全部 messages 再寄给模型一次。不压缩，长任务会在中途把窗口撑满，或者把账单撑爆。这一章用手算看清楚这件事，再写一个笨但诚实的截断器。

这一章只要记住

上下文不是「模型的记忆芯片」，是你每次调用 API 时贴进去的那份列表。列表越长，每一轮越贵。压缩的目标：让模型仍能继续干活，同时丢掉已经过时的观察。

先建立直觉：不是「记住了」，是「每次重读」

生活比喻

你请的帮手每次开口前，都要把到目前为止的全部对话录音从头听一遍。第一轮听 1 分钟；第十轮听 10 分钟。他并没有在脑子里存档——是你每次把整盘磁带塞给他。这就是为什么第 3 轮已经很贵，第 30 轮会贵得离谱。

云端 API 通常按「读了多少 token + 写了多少 token」收费。token 可以先粗想成「一小截字」。中文大约每 1～2 个字一个 token，代码里的空格和符号也算。精确规则因模型而异。miniharness 更糙：直接把字符串长度加起来当预算，不真的去分词。方向对就行。

手算三轮，看见平方感

假设每一轮新产生 100 个 token 的内容（一句人话或一次工具输出），而且每次调用都把旧的全部再读一遍：

轮次这次要读的旧东西这次新写出的到目前累计读过
1100（系统+用户）100100
2200100300

累计阅读量大致按「轮次 × 轮次」往上走。这就是人口中的 O(n²)：n 是轮数，费用大约跟 n 的平方成正比。真实系统会用「缓存前缀」打折——如果你每次请求的开头一模一样，云端可以少算一部分。打折不等于免费：你一旦在列表中间改了一句旧观察，从改动点往后的缓存就作废了。

所以压缩策略不仅是「删东西」，还是「尽量别改已经寄过的前缀」。miniharness 的截断器故意从最老的工具观察动手，并保留最近几条完整对话——这是教学版，不是最优版。

不压缩会发生什么

  1. 模型窗口有上限。超了，API 直接报错，循环崩在半路。
  2. 即使没超，早期那些已经过时的 read 结果（文件后来被 edit 改过了）仍占着位子，模型可能根据过期快照做决定。
  3. 账单按二次方爬。演示任务看不出来，过夜跑仓库时会心疼。

一种笨办法：截断旧观察

打开 compact.py 里的 compact_tool_results。规则只有三条：

  1. 估算当前 messages 总字符。没超过上限就原样返回。
  2. 找出所有 role=tool 的消息。这些是最肥、也最容易过时的（文件内容、测试日志）。
  3. 最近 N 条工具观察整段保留。更早的那些，只留开头一小段和结尾一小段，中间写成 … [省略了多少字] …。

模型下一轮仍知道「我曾经读过、曾经改过」，但不再把整份过期源码当事实。若它需要最新内容，应该再 read 一次——这正是我们想要的。

代码怎么对上原理

  • 压缩发生在 complete() 之前，这样寄出去的已经是瘦身版。
  • 我们改的是内存里的 messages。真要对照「压缩前发生了什么」，第 7 章的轨迹文件应在压缩前另存一份，或记录一条 compact 事件。
  • 字符估算很糙（把所有 content 和参数字符串加起来）。生产系统会用模型自己的分词器。教学里糙一点没关系，方向对就行。
  • 等你写自己的 harness，可以在 compact_tool_results 里换成「摘要 + 保留最近观察」。现在不要在循环里再套一次模型调用，测试会立刻依赖真 API。

先别管 · 摘要式压缩

更强的做法是再调一次模型：「把以上工具输出总结成十句话」。效果好，但贵、而且会丢细节（那次测试到底失败在第几行）。教学版只做头尾截断，避免循环里再套一个循环，也避免测试依赖真模型。

自测

  • 为什么压缩优先砍 tool 消息，而不是砍 user 消息？
  • 文件已经被 edit 过，旧的 read 观察还留着，有什么害处？
  • 如果压缩改了列表中间某一条，对「前缀缓存」意味着什么？
自测答案
  1. 用户原话是任务本身，丢掉等于忘题。工具观察又肥又容易过时。
  2. 模型可能根据过期源码再 edit 一次，或认为 bug 还在。磁盘真相和上下文真相分叉了。
  3. 从被改的那一条往后，缓存作废，后面每一轮都可能按全价重算。
