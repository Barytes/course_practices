第四部 · 取舍

第 11 章 · opencode：可观测性与重构

当循环还要服务终端、IDE、桌面、多会话并行，print 和随手写的异步链条会先于功能一起崩。这一章把手伸进存根系统：工具调用怎么先记账再执行，录取和执行怎么拆开，工作区服务怎么划范围。迁的过程本身就是教材。

这一章只要记住

仓库 anomalyco/opencode（快照 v1.18.31，2026-09-14；GitHub Search 于 2026-09-16 计 21900 条 PR、8958 条已合并）。看三件事：工具调用如何先记账再执行；服务如何按工作区划范围；v1/v2 并存时他们如何避免「两套真相」。最重要的三次投票是：工具调用当状态机持久化、Effect 把取消变成类型、v2 把「录取输入」和「执行」拆开（#30632）。

规模会改变循环的形状

nanocode 可以在一个文件里写完。一个人、一个终端、一次对话，print 就够了。opencode 不是这个规模：多会话、可分享链接、语言服务器、多家模型、插件、桌面应用。失败模式变成：

  • 你点了取消，工具还在往磁盘写。
  • A 仓库的服务泄漏到 B 仓库。
  • 进程崩溃后，界面说「改好了」，磁盘上只改了一半，日志里没有点名记录。

生活比喻

小饭馆用口头报菜就行。百桌酒楼必须先写菜单存根，再进厨房。客人中途买单走人，存根还能告诉你锅里那道菜该不该倒掉。opencode 在补的就是存根系统。

架构：两套并存的运行时

快照时的诚实画面：产品还在卖 v1，核心正在长 v2。读这个仓库，不要假装只有一张架构图。

左边是已经能扛产品的存根。右边是把存根升级成「录取和执行分开」的账本。迁移期两套 API 同时活着。

v1：SessionProcessor 把一次工具调用当成有身份的状态机，而不是助手文本里的一行字。provider 一流出「要点名」，先写入 pending；开始跑变成 running；结束写成 completed / error。取消和崩溃至少还留着「答应过什么」。

v2（specs/v2/session.md）：sessions.prompt() 先把输入写进耐用的 session_input 收件箱，给你一张幂等回执；执行是另一件事。崩溃后，收件箱里的活还在，不会把「正在跑」的工具默默重放——标成 interrupted，让人看见。

服务按 Location（工作区）划范围：模型目录、权限、文件系统、工具表挂在 Location 上；进程级的只有会话存储和执行协调器。两个窗口打开同一仓库，工作区级服务该共享；打开两个仓库，不该串味。

产品层仍有 agent 模式：build（默认可写）和 plan（只读，跑命令要问）。同一根循环，换的是工具权限集。不要把 Plan 理解成另一种魔法模型。

手算：崩溃发生在「改到一半」

用户说「把 a.txt 改成 hello」。模型点名 edit。miniharness 会先改磁盘，再把观察推进内存——进程若在这两步中间被杀，下次醒来既不知道答应过什么，也不知道改没改完。

v1 的存根把一次工具调用当成有身份的状态机，不是助手文本里的一行字：

v2 再拆一刀（#30632）：人的输入先写进耐用的 session_input 收件箱，给你一张幂等回执；执行是另一件事。

崩溃时两边命运不同：收件箱里的录取还在，可以再 wake；执行侧正在 running 的工具不能当成功重放——标成 interrupted，让人看见。v2 规范写得很狠：abandoned side effects are never silently replayed。

对照刚才的比喻

v1 是先写菜单存根再进厨房。v2 是先给客人一张取餐号（录取），厨房开始做是另一件事（执行）。客人中途走人，取餐号还在；锅里那道菜标「中断」，不要假装上过桌。

Location：范围是架构，不是命名风格

执行路由只从 Session ID 出发，再问这张会话属于哪个 Location（工作区）。挂在 Location 上的：模型目录、权限、文件系统、工具表。挂在进程上的：会话存储、执行协调器。两个窗口打开同一仓库，工作区级服务该共享；打开两个仓库，不该串味。

#35228 收紧 Location 服务，#45705 再把 instance 模块抽出来：进程实例 ≠ 工作区。一张图上画两种寿命，就会出现「A 仓库的语言服务器回答了 B 仓库的问题」。

miniharness 只有一个 Workspace 对象。先把根目录传对。服务图是下一课，代码在上游。

Context Epoch：说明书也要有代数

v2 把模型看见的系统上下文做成不可变的基线，叫 Context Epoch。环境事实、今天的日期、向上发现的 AGENTS.md、当前 agent 的 skill 说明书，都是 Source。第一轮完整观察会在任何用户话变成模型可见之前，先初始化这条基线。源暂时读不到，执行停，prompt 留在收件箱里可重试——不要拿一份空说明书去问模型。

之后每一轮：先 promote 合格输入，再在安全边界对源。变了，就追加一条按时间排列的 System 消息，并和快照一起原子提交。压缩完成之后，下一轮直接从当前完整上下文渲染一条新基线。会话搬到另一个 Location，epoch 清空，目的地重新打基线。

模型切换：已经承认的切换等到当前这轮提供商边界之后再生效，不重启这一轮，也不替换基线。skill 说明书变了，当成一条按时间排列的 System 消息，而不是悄悄改开头——否则前缀缓存作废，第 5 章讲过这件事。

压缩：轨迹仍在，模型看见检查点

每一轮问模型前，runner 估算完整请求是否超过窗口减去预留。超了，且有更早的完整回合可收，就先压缩再跑当前这一轮。

压缩不删轨迹。它替换的是模型看见的那一份：一个隐藏检查点，里面是结构化滚动摘要 + 有 token 上限的近期上下文。提供商原生的 assistant / reasoning / tool 消息不跨过这条边界——前缀一变，带签名的思考块会失败。

开始和结束都是耐用事件。只有 ended 才投影成模型可见的压缩消息。失败或中断的压缩，上一道历史边界继续有效。提供商若以「上下文溢出」拒绝，即使本地估算没预警，也再试一次溢出触发的压缩；第二次溢出或已经有耐用输出之后的溢出，变成普通失败，不循环，不重放半截副作用。

steer 和 queue 不是同一种插话

什么时候变成模型可见人话
steer下一个安全的提供商回合边界，包括当前这排水还在继续时「停，改主意了」
queue当前这排需要继续时先排队；会话否则就要闲下来时，一次只 promote 一条 FIFO「做完再看这句」

进程级的 SessionRunCoordinator 让同一会话的执行串行，不同会话可以并行。重复的 wake 会合并。interrupt 停的是本进程正在跑的，不删收件箱。

规范写明：崩溃后的自动续跑是刻意推迟的。wake 不会因为「输入已经 promote 过」就推断提供商那边的活可以安全重试。要续，用显式 run，从耐用投影接着走。

工具表、权限、以及 bash 并没有进沙箱

进程级有一份 ApplicationTools，每个 Location 再叠自己的 ToolRegistry。会话没写 agent 时，执行和权限都走默认的 build。不能让人看见 build 模型的行为，权限却按「没有 agent」的空策略在评。

v2 的 read：相对 Location 解析路径，拒绝绝对路径、逃逸、符号链接逃逸，大文件按行分页。v2 的 bash 规范写得很诚实：生成的壳带着宿主用户的文件系统、进程和网络权限，不是沙箱。绝对路径参数的扫描只是劝告。要隔离，去看 Codex，或自己在外层容器化。

apply_patch 先解析全部 hunk，再批准外部目录，再预先检查，再按顺序提交。中途失败会留下「已经改了的那几处」+ 一份部分应用报告。不要幻想有自动回滚——那是后续票，不是隐含承诺。

plan 模式是权限集。#43710 允许 plan 只写 PLAN 文件；#46905 又把默认收回成「先讨论」。同一根循环，拧的是「能写什么、要不要问人」。

插件双出口，以及 Effect 先别怕

迁移期一个包可以同时 export v1 server() 和 v2 setup()。适配器写两遍，换来旧插件不在迁移周集体死亡。谁是源、谁是适配器，以当时 specs 为准。

Effect 的人话：TypeScript 里一套处理失败、取消、依赖、追踪的库。Agent 运行时充满长时间运行和必须清理的资源。用类型把取消写成可检查的东西，代价是学习曲线，以及旧写法与新写法并存。桌面主进程先迁（#26148），再砍核心——先从外壳练刀。

怎么读一个正在重构的巨仓

不要从根 README 线性读到第 400 个包。去 releases 搜 v2、effect、session。点进 PR 看他们删了哪条旧 API。并存期的仓库，任何「全书架构图」隔周就错。动态读，是唯一不自欺的方法。

自测

  • 为什么「先执行工具，成功了再写日志」在崩溃时会撒谎？
  • Plan 模式换的是模型，还是工具权限？
  • #30632 把 prompt 拆成录取和执行，崩溃时哪一边还在？
  • 同一条 message id 把 prompt 再提交一次，v2 会怎样？
  • v2 规范里的 bash，算不算沙箱？
  • steer 和 queue 哪一个会在当前这排水还在继续时插进模型可见历史？
自测答案
  1. 工具可能已经改了半个文件，日志却说「没做过」。下次恢复会按「没做过」再改一次，或按「做过」跳过——两种都可能是错的。先记账，崩溃后至少知道答应过什么。
  2. 首先是工具权限（以及要不要问人）。模型可以是同一个。
  3. 收件箱里的录取还在，可以再 wake。执行侧正在跑的工具不能当成功重放，要标 interrupted。这就是「存根还在、锅里的菜另说」。
  4. 同一张幂等回执，不另写一行。换了 session、正文或投递模式再复用这个 id，才会失败。
  5. 不算。规范写明生成的壳带着宿主用户权限。路径劝告不是边界。
  6. steer。queue 要等当前这排不再需要继续、会话否则就要闲下来，一次 promote 一条。
