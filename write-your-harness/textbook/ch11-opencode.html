第 11 章 · opencode：可观测性与重构

当循环还要服务终端、IDE、桌面、多会话并行，print 和随手写的异步链条会先于功能一起崩。opencode 把「能看见、能取消、能恢复」当成一等公民，并且正在把旧架构迁到新架构——迁的过程本身就是教材。

这一章只要记住

仓库 anomalyco/opencode（快照 v1.18.31，2026-09-14）。看三件事：工具调用如何先记账再执行；服务如何按工作区划范围；v1/v2 并存时他们如何避免「两套真相」。不必学会他们用的那套函数式运行时。

规模会改变循环的形状

nanocode 可以在一个文件里写完。一个人、一个终端、一次对话，print 就够了。opencode 不是这个规模：多会话、可分享链接、语言服务器、多家模型、插件、桌面应用。失败模式变成：

  • 你点了取消，工具还在往磁盘写。
  • A 仓库的服务泄漏到 B 仓库。
  • 进程崩溃后，界面说「改好了」，磁盘上只改了一半，日志里没有点名记录。

生活比喻

小饭馆用口头报菜就行。百桌酒楼必须先写菜单存根，再进厨房。客人中途买单走人，存根还能告诉你锅里那道菜该不该倒掉。opencode 在补的就是存根系统。

三件你该带走的东西（路径可能已搬家）

  1. 先记账，再执行。工具调用在动手之前先落到可靠存储。授权钩子打在执行前。崩溃后你知道「已经答应做什么」，而不是磁盘上留下半截、日志里没有。
  2. 会话事件可以投影回来。不要只靠内存里的数组。进程死了，应能从记录重建「模型看见过什么」。
  3. 服务有范围。全局的（配置、模型目录）和工作区级的（这个 repo 的语言服务器）不要混在一张表里。混了就会串味。

对你自己的 harness：不必上他们那套运行时库。要上的是事件 + 取消 + 「先记后做」。miniharness 的 events 列表是起点；真正持久化是下一课，代码在上游，不在我们包里。

「Effect」这个词先别怕

你在 release 和博客里会反复看见 Effect。人话版：它是 TypeScript 里一套帮你处理「失败、取消、依赖、追踪」的库。Agent 运行时充满长时间运行、中断、竞赛、必须清理的资源。用库把这些写成可检查的类型，代价是学习曲线，以及迁移期旧写法与新写法并存。

先别管

Layer、LayerNode、OpenTelemetry 的具体 API。问三个问题就够：一次工具在执行前写了什么？kill -9 之后还能否知道？两个窗口打开同一仓库，工作区级服务是共享还是隔离？

产品层仍有 agent 模式

文档里常见两种：build（默认可写）和 plan（只读，跑命令要问）。同一根循环，换的是工具权限集。这和 Codex 的「沙箱 × 审批」、dsh 的 agent 预设是同一类旋钮。

不要把「Plan 模式」理解成另一种魔法模型。它首先是 harness 策略：这一轮允许哪些手、要不要先问人。

怎么读一个正在重构的巨仓

不要从根 README 线性读到第 400 个包。去 releases 搜 v2、effect、session。点进 PR 看他们删了哪条旧 API。并存期的仓库，任何「全书架构图」隔周就错。动态读，是唯一不自欺的方法。

和 miniharness 的距离

他们有我们有你下一步可以补
执行前持久化只在内存 append每次 tool_start 先写一行 JSONL
可取消的运行时没有取消Ctrl-C 时设标志，bash 用超时
按工作区隔离的服务一个 Workspace 对象先别做服务图，把根目录传对就行

读这个仓库时问什么

  • 一次工具调用在执行前写了什么记录？进程被强杀之后能否知道？
  • 两个窗口打开同一 repo，工作区级服务是共享还是隔离？
  • 插件 API 的新版和旧版谁是源，谁是适配器？

自测

  • 为什么「先执行工具，成功了再写日志」在崩溃时会撒谎？
  • Plan 模式换的是模型，还是工具权限？
自测答案
  1. 工具可能已经改了半个文件，日志却说「没做过」。下次恢复会按「没做过」再改一次，或按「做过」跳过——两种都可能是错的。先记账，崩溃后至少知道答应过什么。
  2. 首先是工具权限（以及要不要问人）。模型可以是同一个。
